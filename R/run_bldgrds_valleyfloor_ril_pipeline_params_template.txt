# Pipeline config file for run_bldgrds_valleyfloor_ril_pipeline.R
#
# "keyword: value" lines (same rules as bldgrds_enforce.R's/valleyfloor.R's/RIL.R's own parameter
# files -- order within a section doesn't matter, blank lines and lines starting with "#" are
# ignored, a trailing "# comment" after a value is stripped, and only the first colon on a line
# separates the keyword from its value, so a value like "c:\..." is safe), grouped under four
# section headers: [dem], [bldgrds_enforce], [valleyfloor], [ril].
#
# [dem] takes exactly one line -- dem: <path> -- used for every stage below. Do NOT set dem,
# input_file, or (in [valleyfloor]) data_id in any of the three per-stage sections: this pipeline
# forces the single [dem] value onto all three stages so the DEM-derived data ID that links
# bldgrds_enforce's node database -> valleyfloor's channel definition -> valleyfloor's own
# per-channel data file -> RIL's height-/depth-above-channel input stays identical across all
# three; a line setting any of those three keywords in a per-stage section is dropped with a
# warning rather than honored.
#
# See param_specs in bldgrds_enforce.R/valleyfloor.R/RIL.R for the full keyword list and defaults
# for each section -- everything below is transcribed from those scripts' own reference-project
# templates (Skykomish for bldgrds_enforce, Cherry for valleyfloor, Post Mortem for RIL), with dem
# lifted out to [dem] and each script's own executable_dir left pointing at its own project's
# build output (bldgrds under GridUtilities; valleyfloor/RIL under ChannelUtilities). Replace
# every path below with your own project's before running this for real -- these three reference
# projects are not the same DEM and mixing them as-is will not produce a meaningful result.
